## 1. 背景与问题

### 1.1 业务背景

企业用户在飞书 Windows 客户端中频繁执行搜索操作（联系人、文档、功能入口）。传统 UI 自动化（Selenium、Appium、Accessibility Tree）对**封闭桌面客户端**无效，飞书也未暴露可供测试脚本调用的公开 UI 接口。

### 1.2 核心痛点

| 痛点 | 描述 |
|------|------|
| 无法自动化桌面端 | DOM/控件树方案不可用 |
| 人工回归成本高 | 单条搜索链路手动约 1–5 分钟（含验证） |
| UI 迭代快 | 固定坐标/模板易失效 |
| 缺乏可复现记录 | 失败时难以定位是哪一步出错 |

### 1.3 项目目标（M2 范围）

在**限定场景**内实现可演示、可度量、可归档的自动化能力：

> **用户指定搜索词 → Agent 自动完成飞书全局搜索并进入第一条结果 → 生成执行报告。**

不在 M2 范围内：多场景（审批、日历创建）、自然语言任务理解、Overlay 产品化 UI。

## 4. 非功能需求

### 4.1 可靠性

| 指标 | 目标 | 实测 |
|------|------|------|
| M1 单步成功率 | ≥ 80% | **62.5%**（未达标） |
| M2 流水线 Step01–04 | 稳定可演示 | **77.4%**（31 次历史运行） |
| Demo 模式 3 用例 | 演示可用 | 3/3（固定坐标，2026-05-06） |

### 4.2 性能

| 指标 | 说明 |
|------|------|
| 单次 VLM 调用 | 约 5–30s（含网络） |
| 完整单用例（VLM 模式） | 约 3–5 分钟（含 4×30s Step 间等待 + API 调用） |
| 截图压缩 | 最大 1280×800，降低超时与 Token 消耗 |

### 4.3 可维护性

- 每步独立 Python 模块，统一 `{"success", "message", "screenshot"}` 返回协议
- 敏感配置通过 `.env` 注入
- Git 版本管理，每次修复有 commit 可追溯

### 4.4 安全与合规

- API Key 不得提交至仓库（`.env` 在 `.gitignore`）
- Agent 运行期间完全控制键鼠，需人工确认环境安全
- 仅操作本地已登录的飞书客户端，不采集用户数据外传

## 6. 约束与假设

### 6.1 环境约束

- 操作系统：Windows 10/11
- 飞书：Windows 桌面客户端（中文界面）
- Python：3.10+
- 网络：可访问火山方舟 API

### 6.2 设计假设

1. 飞书窗口可见且未被最小化
2. 搜索框位于屏幕上方区域（OpenCV `max_y_ratio=0.25`）
3. 第一条搜索结果位置相对稳定（Demo 模式依赖固定坐标）
4. VLM 可理解中文 UI 截图并返回 `x=数字,y=数字` 格式

### 6.3 已知未解决项

- 多显示器 / DPI 缩放导致坐标系不一致
- OpenCV 模板随飞书版本过期
- VLM TPM 配额限制下的长时间批量运行

## 7. 需求与实现差距（诚实清单）

| 对外曾声称 | 实际情况 |
|-----------|----------|
| E2E 100% 通过率 | VLM 模式历史约 77.4%；Demo 固定坐标 3/3 |
| 纯视觉、无硬编码 | 存在 `USE_FIXED_COORDS`；Step01 用模板图 |
| 自然语言指令 | CLI + JSON 配置 |
| 10× 效率提升 | 单用例约 3–5 分钟（含防 429 等待） |
| Overlay 产品 UI | 已搁置 |
| 零维护、UI 变化自适应 | VLM 有适应力，但模板与坐标仍须维护 |

## 8. 验收标准（当前版本）

视为「M2 工程验收通过」需满足：

1. `python run_all.py --run-all` 在 VLM 模式下可完整跑通（允许偶发失败，有重试与报告）
2. 每次运行产生 `reports/execution_report_*.md` 与 `archive/` 归档
3. `python tools/run_vlm_benchmark.py --historical` 可复现统计报告
4. 文档（README、本文件、SYSTEM_DESIGN）与代码行为一致
