> 2026-04-29 | 产品架构决策文档

## 一、背景与定位

### 当前问题

我们之前的技术路线是**纯 Python 脚本**（pyautogui + OpenCV 模板匹配），在开发过程中暴露了几个根本性问题：

1. **OpenCV 模板匹配不适合动态内容**——搜索结果布局会随搜索词/时间/用户状态变化，模板图经常失效
2. **没有状态可视化**——Agent 在做什么、做到哪一步了，用户完全不知道
3. **没有安全机制**——用户碰鼠标时 Agent 可能误操作
4. **产品感不足**——纯脚本跑通 = 工具，不是产品

### 目标定位

做一个**桌面 AI Agent**，参考 Kimi 的交互模式，针对飞书场景落地。核心能力：

> Agent 理解飞书界面 → 自动执行操作 → 用户全程可见可控

## 三、核心设计理念（参考 Kimi 的交互模式）

| 设计 | 说明 | 用户体验 |
|------|------|---------|
| **Overlay 卡片** | 右侧半透明悬浮窗，展示 Agent 状态 | "我知道 Agent 在干嘛" |
| **步骤可视化** | 每一步操作实时显示在卡片上 | 减少等待焦虑 |
| **特殊鼠标样式** | Agent 控制时鼠标变大变亮，带状态颜色 | 一眼区分"谁在操作" |
| **用户接管检测** | 检测到用户碰鼠标 → 自动暂停 + 弹出询问 | 安全感 + 控制权 |
| **决策点询问** | 关键操作前让用户确认 | Human-in-the-loop |
| **结果验证** | 点击后对比截图，确认操作成功 | 可靠性保障 |

### 鼠标状态系统

```
🔵 蓝色柔和光圈  → Agent 空闲 / 等待中
🟡 黄色脉冲动画  → Agent 正在分析 / 定位中（还没动鼠标）
🔴 红色大圆+十字  → Agent 正在控制鼠标（⚠️ 请勿触碰）
✅ 绿色闪烁      → 操作完成 / 成功
⏸️  灰色暂停图标  → 用户已接管，Agent 暂停
```

## 四、技术选型

| 层级 | 技术 | 原因 |
|------|------|------|
| **Overlay UI** | tkinter (Python 内置) 或 PyQt5 | 无需额外依赖，跨平台 |
| **VLM 引擎** | 豆包2.0 (方舟平台) | 已有 API Key，支持多模态 |
| **固定UI元素定位** | OpenCV 模板匹配 | 搜索框等固定元素，快且准 |
| **动态内容定位** | VLM 语义理解 | 搜索结果等动态内容，不受布局影响 |
| **桌面操作** | pyautogui | 成熟稳定 |
| **截图** | PIL/Pillow | 快速全屏截图 |

### 核心技术策略：双模态定位

```
固定元素（搜索框、按钮）  →  OpenCV 模板匹配  →  快（<100ms）、准（>0.95置信度）
动态内容（搜索结果）      →  VLM 语义理解      →  慢（3-5s）、但鲁棒
```

## 七、关键决策记录

### 为什么不做"两条线并行"？

**原想法**：线A（快速脚本跑通交差）+ 线B（产品化最终形态）
**最终决定**：直接走最终形态

原因：
1. 两套代码架构完全不同，线A的代码几乎不能复用到线B
2. 线A能积累的只有"踩坑经验"，最大成本（架构/交互/UI）要重来
3. **评委看的是产品完整度**——有 Overlay + 可视化 + 安全机制的 MVP 分数远高于纯脚本
4. 时间有限，集中火力做一件事情更好

### 为什么选择 tkinter 做 Overlay？

- Python 内置，零额外依赖
- 支持 `always-on-top`（置顶窗口）
- 支持透明度（`alpha` 属性）
- 可以做成无边框悬浮卡片
- 如果后续觉得不够好看，可迁移到 PyQt5（接口不变）

## 八、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| VLM API 限流(429) | 操作延迟 | 指数退避重试；缓存常见场景坐标 |
| VLM 定位不准确 | 点错位置 | 二次确认机制；点击后验证 |
| 用户抢鼠标 | 坐标偏移 | 实时检测；自动暂停 |
| tkinter 性能 | UI 卡顿 | 主线程只跑 UI，Agent 在子线程 |
| 比赛时间紧 | 功能做不完 | 先保证核心流程跑通，UI 从简 |
